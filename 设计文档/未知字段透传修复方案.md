# 未知字段透传（Unknown-Field Passthrough）修复方案

> 基线：`main` = `be8fc4c`（本次会话提交后）。所有 `文件:行号` 均来自实际源码。
> 状态：**待实施**（本文只给方案，不含代码改动）。

---

## 1. 背景与实测证据

### 1.1 缺陷

`ChatCompletionRequest`（`src/models/requests.rs:154-193`）是**逐字段结构体**，没有
`#[serde(flatten)] extra`。而 `build_request_body_generic`
（`src/handlers/request_body.rs:46`）的 `Chat` 分支是**从结构体逐字段重建 JSON body**
再发往上游。两者叠加的结果：客户端传来的任何**未在结构体中声明**的字段都会被静默丢弃。

### 1.2 实测（线上网关 `192.168.10.121:8000`）

客户端发：

```json
{"model":"...","messages":[...],"stream":false,"max_tokens":4,
 "prompt_cache_key":"session-probe-cachekey-1","prompt_cache_retention":"24h"}
```

入库的请求体只剩 `['max_tokens','messages','model','stream']` ——
`prompt_cache_key` / `prompt_cache_retention` 被吞。而上游能正常接受这两个字段（实测 200 OK）。

### 1.3 为什么这是「比会话 id 更广」的问题

会话 id 缺失只是它的一个症状。实际上 vLLM / SGLang / OpenAI 生态里大量**采样与路由参数**
都落在这个盲区里：

| 类别 | 典型被吞字段 |
| :--- | :--- |
| 缓存/路由 | `prompt_cache_key`、`prompt_cache_retention`、`safety_identifier` |
| 采样扩展 | `top_k`、`min_p`、`typical_p`、`tfs`、`repetition_penalty`（部分端点）、`seed`（部分端点） |
| vLLM 专有 | `guided_json`、`guided_regex`、`guided_choice`、`guided_grammar`、`enable_thinking`、`thinking_budget`、`include_stop_str_in_output`、`ignore_eos`、`skip_special_tokens`、`truncate_prompt_tokens`、`priority`、`spaces_between_special_tokens` |
| 结构化输出 | `response_format`、`json_schema`、`structured_outputs` |
| 工具/多轮 | `parallel_tool_calls`、`tool_choice`（部分形态）、`functions`/`function_call`（旧式） |
| 审计/合规 | `user`、`metadata`、`store`、`moderation` |

一个真实后果：客户端配了 `guided_json` 期望结构化输出，网关静默丢弃后模型返回自由文本，
**没有任何报错**——排查成本极高。

## 3. 三个方案对比

### 方案 A：给每个结构体加 `#[serde(flatten)] extra`，重建时先展开 extra 再覆盖已知字段

```rust
// src/models/requests.rs
pub struct ChatCompletionRequest {
    // ... 现有字段 ...
    #[serde(flatten)]
    pub extra: serde_json::Map<String, Value>,
}
```

```rust
// src/handlers/request_body.rs  Chat 分支开头
let mut body = serde_json::Map::new();
// 1. 先铺未知字段（最低优先级）
body.extend(p.extra.clone());
// 2. 再写已知字段（覆盖同名键）
body.insert("model".into(), json!(p.model));
body.insert("messages".into(), json!(p.messages));
body.insert("stream".into(), json!(stream));   // 强制覆盖
// ... 其余已知字段同上 ...
let mut body = Value::Object(body);
```

| 维度 | 评价 |
| :--- | :--- |
| 改动面 | 中：6 个结构体 + 6 处重建逻辑；但每处都是同一个模式 |
| 语义清晰度 | **好**：优先级显式（extra 最低，已知字段覆盖），`model_rewrite` / 强制 `stream` 仍是最后一步，语义不变 |
| `stream_options` 双写风险 | 无：已知字段显式 `insert` 覆盖 extra 里的同名键 |
| 审计库影响 | 中性：`request` 列存的就是重建后的 body，现在**更接近真实上游请求**（更准确，体积随客户端字段增加） |
| 风险 | 客户端可借此注入任意字段到上游——但这本来就应该允许（网关是透传代理，不是字段白名单） |
| 缺点 | 需要逐个结构体改，漏一个就仍会吞字段 |

### 方案 B：路由层保留原始 `Bytes`，以原始 JSON 为基底做定点修改

结构体只用于提取路由/统计信息，发往上游的 body 直接基于原始 JSON 修改。

| 维度 | 评价 |
| :--- | :--- |
| 改动面 | **大**：`CustomJson` 需同时交出 raw bytes；`handle_request_logic` 签名变更；流式/非流式/音频三条路径都要改 |
| 语义 | 最忠实（真正「透传」） |
| `model_rewrite` 交互 | 干净：仍是最后一步改 `model` |
| 内存 | **差**：body 可达 64 MiB（`MAX_REQUEST_BODY_BYTES`），需同时持有 raw bytes 与解析后的结构体；当前已在 `CustomJson` 里 `bytes.to_vec()` 一份给 simd-json，再留一份会翻倍 |
| 审计库影响 | **显著变差**：`request` 列会存原始体（含客户端所有字段），压缩率下降、库体积上涨 |
| 风险 | 需要小心 `stream` 强制覆盖与 `stream_options` 注入的落点 |
| 优点 | 一次性解决所有端点（含未来的新端点） |

### 方案 C：白名单透传

维护「允许透传给上游的未知字段白名单」，其余仍丢弃。

| 维度 | 评价 |
| :--- | :--- |
| 改动面 | 小 |
| 维护成本 | **高**：vLLM/SGLang 每个版本都在加字段，白名单永远滞后 |
| 是否解决根本问题 | **否**：仍然是「网关猜测客户端意图」，只是把黑名单换成白名单 |
| 安全性 | 最高（但也最没用） |

### 结论

**推荐方案 A**，理由：

1. 改动模式统一（6 处同一套写法），可逐个端点独立提交、独立回滚；
2. 与现有 `extra_body` 机制（`src/config/types.rs:39`，`apply_extra_body_cached`
   `src/handlers/request_body.rs:92` 的语义是「**只在缺失时补**」）方向一致，
   都是「客户端/配置给什么就带什么」；
3. 内存与审计库体积影响可控（仍只存重建后的 body）；
4. 不需要改 `CustomJson` / handler 签名这类高耦合部位。

方案 B 的「真正透传」优势在**未来**更值得考虑（尤其若要做多模态/新协议），
但当前改动成本与内存代价不成比例，暂不采用。

## 4. 推荐方案的详细改动清单

### 4.1 结构体（`src/models/requests.rs`）

给 6 个结构体各加一个字段。注意**必须是最后一个字段**且不与现有字段名冲突：

```rust
/// 未在结构体中声明的字段，原样透传给上游。
///
/// 网关是透传代理，不应猜测客户端会用哪些扩展字段：vLLM / SGLang / OpenAI
/// 生态持续新增采样与路由参数（`top_k`、`guided_json`、`prompt_cache_key`…），
/// 逐字段声明必然滞后，且丢弃时**不会报错**，排查成本极高。
#[serde(flatten)]
pub extra: serde_json::Map<String, Value>,
```

适用：`ChatCompletionRequest`、`CompletionRequest`、`EmbeddingRequest`、
`RerankRequest`、`ScoreRequest`、`ClassifyRequest`。

> `EmbeddingRequest` 已有 `user: Option<String>` 字段（`:230`），它会被 serde 正常
> 反序列化，不会落进 `extra`，因此不冲突。

### 4.2 重建逻辑（`src/handlers/request_body.rs`）

`Chat` 分支（`:112`）与 `Completion` 分支（`:175`）改为「先铺 extra、再覆盖已知字段」。
`Embedding` / `Rerank` / `Score` / `Classify` 四个分支走 `serde_json::to_value(p)`
（`:212-215`），**加了 `flatten extra` 后自动就正确**，无需改动——这是方案 A 的一个
额外好处。

关键代码（Chat 分支）：

```rust
RequestPayload::Chat(p) => {
    let adjusted_max_tokens = adjust_max_tokens(client_config.max_tokens, p.max_tokens);
    let merged_stop = merge_stop_words(client_config.stop.as_ref(), p.stop.clone());

    // 1. 未知字段垫底：客户端显式发来的字段优先于网关默认值，
    //    但低于下面所有显式已知字段（避免客户端用 extra 覆盖 model/stream）。
    let mut body: serde_json::Map<String, Value> = p.extra.clone();

    // 2. 已知字段覆盖
    body.insert("model".into(), json!(p.model));
    body.insert("messages".into(), json!(p.messages));
    body.insert("stream".into(), json!(stream));      // 网关对 stream 有最终决定权
    // ... 其余字段保持现有 if let Some(..) 逻辑，改为 body.insert(...) ...

    if stream {
        // stream_options：客户端给了就用客户端的，否则注入 include_usage。
        // 注意这里用 insert 覆盖 extra 里的同名键，绝不会产生两份。
        let opts = p
            .stream_options
            .clone()
            .unwrap_or_else(|| json!({"include_usage": true}));
        body.insert("stream_options".into(), opts);
    } else {
        // 非流式时不应把客户端的 stream_options 透传给上游。
        body.remove("stream_options");
    }

    Value::Object(body)
}
```

### 4.3 与既有特性的交互（必须保持不变）

| 特性 | 落点 | 加了 extra 后是否受影响 |
| :--- | :--- | :--- |
| `model_rewrite` 模型名改写 | `build_request_body_generic` 最后调用 `rewrite_body_model`（`:70`） | **不受影响**：仍在最外层最后执行，是 `model` 的最终权威 |
| `extra_body` 配置注入 | `apply_extra_body_cached`（`:50`） | **不受影响**：仍是「只在缺失时补」，优先级低于客户端字段——语义不变 |
| 强制 `stream` 覆盖 | Chat 分支显式写 `stream` | **不受影响**：显式 `insert` 覆盖 extra |
| 流式 `stream_options` 注入 | Chat 分支 `if stream` | **需注意**：必须 `insert` 覆盖而非 `extend`，否则可能出现两份 |
| 思考格式归一化 | `thinking_transformer.rs` | 不受影响（作用于响应/消息内容） |

**关于 `stream_options` 的现状确认**：客户端显式传 `stream_options: {"include_usage": false}`
时，当前行为是**原样使用客户端的值**（`request_body.rs:153-155` 的 `if let Some(opts)`）。
加了 extra 后仍应保持这一行为——上面的代码用 `p.stream_options.clone().unwrap_or_else(...)`
正是为了维持它，并保证不与 extra 里的同名键冲突。

### 4.4 配置开关（建议）

默认**开启**透传（这是修正既有缺陷，不是新功能）。提供一个环境变量供极端情况回退：

```bash
PASSTHROUGH_UNKNOWN_FIELDS=true   # 默认 true；false 时退回逐字段重建（旧行为）
```

命名与仓库现有风格一致（`MAX_REQUEST_BODY_BYTES`、`RECORD_STORE_RAW_CREDENTIALS`、
`LOG_FULL_TOKEN_ON_ERROR`）。实现上用一个 `once_cell::sync::Lazy<bool>` 读取一次即可，
与 `src/db/extract.rs:32` 的 `STORE_RAW_CREDENTIALS` 同款。

> 若担心安全，可另加 `PASSTHROUGH_UNKNOWN_FIELDS_DENY`（逗号分隔的字段名黑名单），
> 但**不建议默认非空**：任何默认黑名单都会重新引入「静默丢弃」问题。

## 6. 回归风险与验证

| 风险 | 缓解 |
| :--- | :--- |
| 客户端注入恶意字段撑大上游请求 | 已有 `MAX_REQUEST_BODY_BYTES`（默认 64 MiB）兜底；审计库 `RequestBytes` 可观测 |
| 客户端覆盖 `model` 绕过路由 | 不可能：`rewrite_body_model` 最后执行，且路由匹配早已在 `dispatcher` 完成 |
| 客户端覆盖 `stream` 导致响应形态不符 | 不可能：Chat/Completion 分支显式 `insert("stream", stream)` |
| 审计库体积上涨 | 预期小幅上涨（只多出客户端本就发送的字段）；`RECORD_ZSTD_LEVEL` 与 `AUDIT_FTS_*` 已可调 |
| 某些上游对未知字段报 422 | 这是**客户端与上游**之间的事，网关不应代为过滤；如确需过滤用 `extra_body` 反向覆盖或未来的 deny 列表 |

## 7. 不做什么（边界）

- **不做字段白名单/黑名单默认值**：任何默认过滤都会重新引入「静默丢弃」。
- **不改 `CustomJson`**：不引入 raw-bytes 双持（方案 B），避免 64 MiB 级别的内存翻倍。
- **不改 schema**：`records` 表结构不动；`request` 列存的仍是重建后的 body。
- **不代理响应侧的未知字段过滤**：响应本来就直接透传。
- **不为 `ResponsesRequest` / `AnthropicMessagesRequest` 做任何改动**：它们已经正确。
