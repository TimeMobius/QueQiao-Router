# 中文检索性能对比

测试日期：2026-10-23（UTC）。

## 数据与环境

- 源库原件：`/tmp/record.db`，SQLite schema v7，108,895 条审计记录。
- 同盘预跑的源库副本：`/mnt/data/qq-migrate/source-v7-bench.db`。
- 迁移目标库：`/mnt/data/qq-migrate/v8-real.db`，Turso 0.8.3，schema v8。
- 正式主对照：源库 `/tmp/record.db`，目标库只读副本 `/tmp/opencode/target-v8-bench.db`，两端均在 tmpfs 上。
- 原件和源库测试副本 SHA-256：`b09b9bd475708c52cb017e1941ac67280b62e740ca062069201b18969036ae95`。
- 源库 11,547,865,088 字节，目标主文件 11,654,012,928 字节。
- ZFS 同盘预跑中源库单字扫描出现约 34.5 秒的延迟，而先前 tmpfs 上相同查询约半秒。为避免将存储/cache 条件误判为引擎速度，主对照将目标库也复制到 tmpfs。这个主对照不代表持久化存储性能。
- CPU：Intel Core i7-14650HX；系统内存约 32 GiB，无 swap。
- 测试使用 release Rust 程序，在同一进程内打开源 SQLite 和目标 Turso，只读、串行执行，不包含 CLI 启动和 HTTP 网络时间。
- 两端均复用一个已打开的连接；每场景一次预热，随后五次采样，源/目标交替执行顺序。
- 不清理全局文件缓存，不代表冷启动、NFS、多用户并发或带写入负载的性能。
- 尤其不能将复用单连接的结果直接当作当前 ReaderPool 每次新建连接的 API 延迟。

## 查询与统计口径

- 源 V7：不足 3 字使用三个文本列的 LIKE；至少 3 字按 V7 的全文查询构造方式使用 FTS5 trigram。
- 目标 V8：至少 2 字使用 SearchText 的 ngram FTS 和 instr 残余条件；1 字使用 SearchText LIKE。
- 计数、按时间倒序取 51 条列表分别测量；补充最近 1 天、最近 7 天、状态和模型条件。
- 列表完整消费结果，查询错误直接失败；同时报告命中数与前 51 条 ID 一致性。
- 每个场景先独立预热，再重复采样，交替两端执行顺序。小样本报告中位数和最大值，不把最大值称作可靠的 p95。
- 多词、短语与标点查询按实际两版实现对照，结果不同的场景不能解读为等价工作量下的速度差异。

### 性能结论

- 两字词计数：目标 FTS 比源三列 LIKE 有明显优势，例如模型约快 4.7 倍、图片约快 8.9 倍；错误约快 2.7 倍。
- 两字词首页列表：源库能以时间顺序很快找到前 51 条，目标当前实现则明显更慢；模型约慢 22.8 倍，错误约慢 86.9 倍。不能把计数优势推广到列表。
- 三字及以上：本轮有相同结果的场景中，源 FTS5 的完整计数通常快约 11–39 倍，列表通常快约 5–10 倍；绝对延迟因命中规模而异。
- 单字完整计数：目标更慢，且计数有小量差异。单字首页列表很快，两端大致在 0.5–2 毫秒，但这不能掩盖完整计数的成本。
- 时间/状态过滤：当前目标实现没有在这些场景追平源库；例如数据库 + 最近 1 天，计数 114.25 对 8.85 毫秒。
- 这是稳态、单连接、无写入、tmpfs 上的结论。先前磁盘目标库每次开连接的秒级结果不是同一测试口径，不能直接拿来计算本轮倍数。

## 一致性与已证实的语义问题

23 个场景中，完整计数 18 组一致，列表前 51 条 ID 有 21 组一致，封顶计数 21 组一致。封顶计数会掩盖 10,000 条之外的差异。

### NUL 字符，而非 Unicode 折叠

已在源数据中复现：

- `模` 少的 2 行：32531、82103，RequestTail 的第 673、24 个字符分别为 NUL。
- `的` 少的 10 行：32232、32261、32736、41882、42146、72779、81381、85611、85647、85651，RequestTail 均含 NUL。
- `用户` 多的 2 行：41872、41877，RequestTail 的第 197 个字符为 NUL。

直接在源 SQLite 上比较“三列 LIKE”和“同样拼接成 SearchText 后 LIKE”，能重现单字的 2/10 行差异；比较“三列 LIKE”和“拼接后 instr”，能重现用户的 2 行差异。LIKE 在 NUL 处停止匹配，而 instr 能检查其后的文本；拼接还会改变 NUL 对后续字段的影响范围。

因此，之前把这些差异归为 Unicode 折叠是不准确的。此处记录为需在兼容性设计中处理的语义差异，本轮没有修改产品查询逻辑。

### 多词从短语变成 AND

V7 对整个 q 加引号，V8 按空白拆分后用 AND 连接。因此 `数据库 连接`、`数据库 错误码` 的结果分别是 0 对 2,270、0 对 481。它们的耗时只表示当前两种实现各自的成本，不能作为语义等价的引擎速度比较。

## 执行计划证据

Turso `数据库` 的计数查询：

```text
1|0|0|QUERY INDEX METHOD fts
```

Turso `函数调用` 的列表查询：

```text
1|0|0|QUERY INDEX METHOD fts
19|0|0|USE SORTER FOR ORDER BY
```

源 SQLite 的 FTS 查询使用 FTS5 虚表索引取 rowid，再按主键查 records；列表查询额外使用临时 B-tree 排序。

因此，之前仅凭耗时推断“高频词自动退化为全表扫描”的说法没有成立的执行计划证据。这里只报告实测耗时，不将原因归结到未经证明的规划器机制。
